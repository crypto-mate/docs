---
title: "Create holding mirror wallet"
description: "Add an inbound Solana or Stellar address to the card program's holding wallet."
api: "POST /cards/holding/mirror-wallets"
---

<Warning>
  **Send only the assets this address accepts.** A mirror wallet is provisioned for a specific set of assets on its blockchain — the ones listed in `tokens` — and credits nothing else. Which assets those are depends on the blockchain. Any other asset can land at the address and stay there: it is never credited to the holding balance, nothing returns it automatically, and no endpoint recovers it. Check the asset and the blockchain before every transfer — a wrong one is not reversible from the API.
</Warning>

Creates a mirror wallet for the card program's holding wallet: an additional inbound address on another blockchain that funds the same holding balance. Requires an API key with access level 2 or higher.

The request carries no identifier. The company is taken from the API key, and the holding wallet is resolved from it.

The call answers `200`, not `201`. Repeating a call that succeeded returns the mirror wallet the holding already has on that blockchain, instead of creating a second one. A mirror wallet can only be added — there is no way to remove one or replace it with another address.

Solana and Stellar are available. The holding wallet holds at most one mirror wallet per blockchain, so it can have one of each — call the endpoint once per blockchain. Other blockchains are enabled in later developments.

Individual cards have their own program and their own pair of endpoints — see [Create individual cards holding mirror wallet](/api-reference/cards/individual-cards/create-individual-cards-holding-mirror-wallet). A mirror wallet created here funds the enterprise card program only.

## How a mirror deposit reaches the holding balance

A mirror wallet does not move the holding wallet off Polygon. The Polygon address returned by [Get holding balance](/api-reference/cards/holding/get-balance) stays the program's main deposit address and does not change — a mirror wallet is an additional way in, not a replacement.

An accepted asset sent to a mirror address is **not** credited on the blockchain it landed on. It is bridged to the Polygon holding wallet and credited there, so the balance moves once the transfer settles on Polygon, not when the deposit confirms on Solana or Stellar. Expect a delay between the two, and read the balance from [Get holding balance](/api-reference/cards/holding/get-balance) rather than from a block explorer on the mirror blockchain.

<Warning>
  **The 10 USD minimum deposit applies to mirror addresses too.** A deposit below 10 USD is not picked up: it is neither bridged nor credited, and the funds stay at the mirror address. No endpoint recovers them. Send at least 10 USD per transfer.
</Warning>

## Body

Unknown fields are ignored.

<ParamField body="blockchain" type="string" required>
  Blockchain of the mirror wallet. `SOLANA` and `STELLAR` are the values available. Matching is case-insensitive, and the uppercase form is the canonical one.
</ParamField>

## Response

<ResponseField name="address" type="string">
  Inbound address of the mirror wallet on its blockchain.
</ResponseField>

<ResponseField name="blockchain" type="string">
  Blockchain of the mirror wallet. `SOLANA` or `STELLAR`.
</ResponseField>

<ResponseField name="enabled" type="boolean">
  Whether the mirror wallet is receiving deposits. A new mirror wallet comes back `true`. A `false` means the address is not accepting deposits — do not send funds to it while it reads `false`. This is not a state you can change.
</ResponseField>

<ResponseField name="tokens" type="string[]">
  Symbols of the assets this address accepts and credits, in the order the platform provisions them. Which assets these are depends on the blockchain: a `STELLAR` mirror wallet accepts `USDC` and `USDT0`, a `SOLANA` one accepts `USDC`. Anything not in this list is not credited and cannot be recovered — see the warning above.
</ResponseField>

## Rejected blockchains

Two different statuses answer a blockchain the endpoint will not accept, and they tell you different things:

- `400` — the value is not a blockchain CryptoMate knows, such as `NOTACHAIN`. The request fails while its body is being read, before any business rule runs.
- `412` — the value is a blockchain CryptoMate knows but has not enabled for mirror wallets, such as `POLYGON`. A `blockchain` field that is missing or `null` answers `412` as well. The `message` names the blockchains that are enabled.

Neither one is worth retrying — both describe a request that will be rejected the same way every time. Fix the `blockchain` value and call again.

## Provisioning already in progress

A `409` is different: it means another provisioning for the same program and blockchain is still running, so this one was refused to avoid creating two addresses at once. **Retry it.** The lock clears when the first call finishes, and a retry then returns that mirror wallet.

Do not treat a `409` like a `412`. A `412` is permanent and a `409` is not — give up on a `409` and the program is left without the mirror wallet you asked for.

## Provisioning failures

Creating the address takes several on-chain steps, and which ones depends on the blockchain: a Stellar address is funded and given a trustline for each asset it accepts, a Solana address is funded for rent and given an associated token account for each. If any step fails, the call answers `500` with a generic message and no internal detail.

Retrying is safe — you end up with a program that has a usable mirror wallet. What a retry does not do is hand you back the address the failed attempt was working on: a call that fails records no mirror wallet for the holding, so the retry provisions and funds a new address. Only a call that already succeeded returns the same wallet when you repeat it.

<RequestExample>

```bash cURL
curl -X POST "https://api.cryptomate.me/cards/holding/mirror-wallets" \
  -H "x-api-key: $CRYPTOMATE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "blockchain": "STELLAR"
  }'
```

</RequestExample>

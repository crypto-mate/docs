---
title: "Create individual card mirror wallet"
description: "Add an inbound Solana, Stellar or BNB Chain address to an individual card."
api: "POST /cards/individual-cards/{cardId}/mirror-wallets"
---

<Warning>
  **Send only the assets this address accepts.** A mirror wallet is provisioned for a specific set of assets on its blockchain — the ones listed in `tokens` — and credits nothing else. Which assets those are depends on the blockchain. Any other asset can land at the address and stay there: it is never credited to the card balance, nothing returns it automatically, and no endpoint recovers it. Check the asset and the blockchain before every transfer — a wrong one is not reversible from the API.
</Warning>

<Note>
  A deposit of an accepted asset at a mirror address is credited to the card balance, the same as a deposit at the address returned by [Get individual card top-up wallets](/api-reference/cards/individual-cards/get-individual-card-top-up-wallets).
</Note>

Creates a mirror wallet for the individual card: an additional inbound address on another blockchain that funds the same card balance. Requires an API key with access level 2 or higher.

The call answers `200`, not `201`. Repeating a call that succeeded returns the mirror wallet the card already has on that blockchain, instead of creating a second one. A mirror wallet can only be added — there is no way to remove one or replace it with another address.

Solana, Stellar and BNB Chain are available. A card holds at most one mirror wallet per blockchain, so a card can have one of each — call the endpoint once per blockchain. Other blockchains are enabled in later developments.

Enterprise virtual cards have the same pair of endpoints — see [Create card mirror wallet](/api-reference/cards/virtual-cards/create-mirror-wallet).

## Path parameters

<ParamField path="cardId" type="string" required>
  Individual card identifier.
</ParamField>

## Body

Unknown fields are ignored.

<ParamField body="blockchain" type="string" required>
  Blockchain of the mirror wallet. `SOLANA` and `STELLAR` are the values available. Matching is case-insensitive, and the uppercase form is the canonical one.
</ParamField>

## Response

<ResponseField name="address" type="string">
  Inbound address of the mirror wallet on its blockchain.
</ResponseField>

<ResponseField name="blockchain" type="string">
  Blockchain of the mirror wallet. `SOLANA` or `STELLAR`.
</ResponseField>

<ResponseField name="enabled" type="boolean">
  Whether the mirror wallet is receiving deposits. A new mirror wallet comes back `true`. A `false` means the address is not accepting deposits — do not send funds to it while it reads `false`. This is not a state you can change.
</ResponseField>

<ResponseField name="tokens" type="string[]">
  Symbols of the assets this address accepts and credits, in the order the platform provisions them. Which assets these are depends on the blockchain: a `STELLAR` mirror wallet accepts `USDC` and `USDT0`, a `SOLANA` one accepts `USDC`. Anything not in this list is not credited and cannot be recovered — see the warning above.
</ResponseField>

## Rejected blockchains

Two different statuses answer a blockchain the endpoint will not accept, and they tell you different things:

- `400` — the value is not a blockchain CryptoMate knows, such as `NOTACHAIN`. The request fails while its body is being read, before any business rule runs.
- `412` — the value is a blockchain CryptoMate knows but has not enabled for mirror wallets, such as `POLYGON`. A `blockchain` field that is missing or `null` answers `412` as well. The `message` names the blockchains that are enabled.

## BNB Chain reuses the card's own address

A BNB Chain mirror wallet is **not a new address**. It is the card's Polygon address, registered so that deposits on BNB Chain are watched too — an EVM address is derived from its key rather than from the network, so the same account already exists on both.

That has three consequences worth knowing before you use it:

- **`address` will match the one you already have on Polygon.** That is expected, not a bug, and not something to report.
- **The network still matters.** The same address on Polygon and on BNB Chain holds two independent balances. Sending BNB Chain USDT and expecting it on Polygon does not work: it is bridged, and the balance moves when that bridge settles.
- **Nothing is created on chain**, so this call has no funding step to fail at — the whole "provisioning failures" section above is about the other two blockchains.

## Provisioning failures

Creating the address takes several on-chain steps, and which ones depends on the blockchain: a Stellar address is funded and given a trustline for each asset it accepts, a Solana address is funded for rent and given an associated token account for each. **A BNB Chain address takes none of them** — see below. If any step fails, the call answers `500` with a generic message and no internal detail.

Retrying is safe — you end up with a card that has a usable mirror wallet. What a retry does not do is hand you back the address the failed attempt was working on: a call that fails records no mirror wallet for the card, so the retry provisions and funds a new address. Only a call that already succeeded returns the same wallet when you repeat it.

<RequestExample>

```bash cURL
curl -X POST "https://api.cryptomate.me/cards/individual-cards/card_6f1e2a30-4a3c-4b2e-9a1d-5e8c9b7a1f23/mirror-wallets" \
  -H "x-api-key: $CRYPTOMATE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "blockchain": "STELLAR"
  }'
```

</RequestExample>
